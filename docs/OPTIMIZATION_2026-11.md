# Kender 工程优化记录（2026-11）

> 这一轮改的不是功能，是**可验证性**和**稳定性**。
> 面试讲项目时，素材都在这份文档里。

---

## 一句话概括

把一个"能演示"的 Agent，改成"能度量、能复现、出错查得到"的工程项目：
建评测体系 → 用评测找出真 bug → 修 bug → 用数字证明修好了。

---

## 五个真实缺陷（都是评测翻出来的，不是拍脑袋想的）

### 1. 模型会凭空编天气

**现象**：问「深圳天气怎么样」，约一半概率在 0.7 秒内直接回 `深圳: 🌦️ 18°C`，
而且全程没有调用过天气工具。

**根因**（两个叠加）：
- `get_weather` 的 docstring 里写了示例输出 `"上海: 🌦️ +31°C"`，模型会直接抄这个格式
- `get_reply_with_review` 在"本轮没调工具"时跳过 Critic 审核 → 假数据直接放行

**修复**：
- docstring 去掉示例数值
- 新增双条件守卫：**问题本身是实时类**（天气/股价/新闻）**且**回答里出现"数字 + 实时特征词"，就强制重写，要求先取证
- 系统提示新增三条硬规则：实时信息必须取证、不得外推未来、多任务不遗漏

**验证**：`eval` 的 W01–W05 从"偶尔失败"变成稳定通过。

---

### 2. Critic 打回重写后，把工具调用记录弄丢了

**现象**：明明调了工具，界面和日志却显示"本轮没有调用工具"。

**根因**：重写轮次通常不再调工具（凭记忆重写），返回的轨迹只反映最后一轮，
而最后一块轨迹是"没有调用工具"这个占位字符串（非空），把真正的轨迹覆盖了。

**修复**：保留 `last_trace_with_tools`，返回时优先用它；重写时把工具原始返回
（`_collect_tool_outputs`）一起喂回去，否则模型看不到数据只能编。

---

### 3. 重写轮会退化成"复读原始数据"

**现象**：重写后回答变成 `深圳: 🌦️ +28°C`——把工具输出原样贴给用户。

**修复**：`_looks_like_echo` 检测"短回答且是工具输出的子串"，判为不合格直接重写。

---

### 4. 搜索要 15 秒，还经常超时

**现象**：搜索类用例 20–100 秒，`ddgs` 实测 12–24 秒，多次 20 秒超时。

**测量**（先量再改）：

| 方案 | 耗时 |
|---|---|
| ddgs 默认（多后端聚合） | 12–24 s |
| ddgs 单后端 | 5 s 但直接报 "No results" |
| DuckDuckGo HTML | 8 s 超时 |
| **cn.bing.com 网页结果** | **0.3 s** |

**修复**：
- `search_web` 改成 provider 链：Bing 优先、ddgs 兜底，可用 `KENDER_SEARCH_PROVIDERS` 配置
- 加 10 分钟 TTL 缓存（同一 query 第二次 0 ms）
- 天气/搜索加指数退避重试，消化公共服务的偶发抖动

**结果**：搜索 **15 s → 0.3 s**，整套 eval 从 8 分钟降到 2 分钟。

---

### 5. 追问后用户只回一个词，模型会再问一遍

**现象**：`帮我查天气` → `哪个城市？` → 用户回 `上海` → 又回 `哪个城市？`（约 50%）

**排查过程**（这条最能说明"看现象"的价值）：
1. 先怀疑模型接不上短回答 → 加提示词规则，没用
2. 加"追问锚定"（把上下文写进本轮输入）→ 好了一些，但仍有一半失败
3. 对比成功/失败两次运行的耗时：**失败 1.3 秒，成功 6 秒**
4. 顺着耗时查代码，发现 `msg.id = f"msg_{int(time.time())}"` —— **秒级时间戳**
5. 两轮对话在 1 秒内完成时 id 撞车，AgentScope 把第二条用户消息当重复消息，
   模型看到的上下文还停在自己上一句问话上，于是原样再问一遍

**根因**：消息 ID 用秒级时间戳生成，快速连轮时重复。

**修复**：改用 `uuid4().hex[:12]`。修复后 MT03 连续 5 次通过。

**教训**：一直没往"框架层 id 冲突"想，是因为假设了"模型不会原样重复一句话"。
把"模型行为异常"和"耗时异常"对上，才找到真正的位置。

## 顺带修的两个工程问题

| 问题 | 影响 | 修复 |
|---|---|---|
| Windows 控制台 GBK 编码 | 模型一输出 emoji 就 `UnicodeEncodeError`，回答变成"调用模型出错" | `src/console.py` 启动时强制 UTF-8，`src/__init__.py` 调用，所有入口生效 |
| `agent.reply` 无超时 | 模型/工具卡住时请求无限挂起，Web 一个请求占死 worker | `asyncio.wait_for` 包一层，默认 120 s，超时转成可读提示 |
| **默认参数在导入时求值**（`db_tool` / `rag`） | `index_dir: str = DEFAULT_INDEX_DIR` 在 import 时就固化了，改环境变量、monkeypatch 全都不生效——测试只能去动真实的 `data/` 目录 | 默认值改成 `None`，函数体内取 `_default_index_dir()` / `DB_PATH`，同时支持环境变量覆盖 |
| FastAPI 共用同一个 agent | 并发请求会把 A 的 `tool_use` 插进 B 的对话，回答串台 | 抽出 `run_chat_turn()` + `asyncio.Lock` 串行化（先保正确性，多会话隔离留待后续） |

**一个反复出现的 bug 模式**：默认参数在**函数定义时**求值，不是调用时。
`db_tool` 和 `rag` 都踩了，症状一样——"配置改了没反应、测试没法隔离"。
现在项目里凡是路径类默认值，都改成运行时解析。

另外把 CLI 从 `get_reply` 改成 `get_reply_with_review`——原来命令行既没有质量审核
也没有编造守卫，和网页端是两套行为。

## 评测体系（这是这一轮的核心资产）

```
eval/
├── cases.jsonl            30 条  基础能力（天气/搜索/填槽/多轮/闲聊/边界/文档）
├── cases_hard.jsonl       12 条  格式约束、抗幻觉、越权、单位换算、指令注入
├── cases_multiturn.jsonl   5 条  跨轮记忆、指代、槽位补全、偏好延续
├── cases_edge.jsonl       10 条  不存在的地点、空输入、冲突约束、三城并发
├── runner.py                    跑批 + 判定 + 报告 + 落库
├── judge_llm.py                 rubric 打分（注入当前日期与工具证据）
├── trace.py                     SQLite：runs / steps 两张表
└── show_trace.py                轨迹查询 CLI
```

**判定分两层：**
- **规则**：工具选对没、格式守没守、有没有禁词（确定性、零成本）
- **LLM**：开放题按 rubric 打分 0/1/2（判定器必须拿到当前日期和工具返回，否则会误判）

**为什么必须上 LLM 判定**：关键词判定连续误伤三次——模型答"严重**失实**"、
"**超出**能力范围"、"**无**降雪"，全被判失败。规则适合测工具，不适合测语义。

**环境失败单独排除**：搜索超时、平台内容审核拦截不算模型能力问题，
不计入通过率，否则基础设施抖动会被误读成模型退化。

## 面试怎么讲（三个 3 分钟故事）

**故事 1：怎么发现"模型在编数据"**
> 我做了 30 条评测，发现天气类题目有约一半会失败，但日志显示"没调用工具"。
> 一开始以为是框架 bug，查了 agent 状态隔离、看了 memory 结构，最后定位到
> 模型在照抄工具 docstring 里的示例格式编温度，而 Critic 在"没调工具"时被跳过。
> 修法是加一个双条件守卫 + 去掉示例，之后这类问题不再出现。

**故事 2：搜索优化**
> 用户抱怨"查个东西要等十几秒"。我先量了一下，ddgs 要 12–24 秒，还有 20 秒超时；
> 换成 cn.bing.com 直接 0.3 秒。于是做成 provider 链 + 兜底 + 缓存，
> 整体快了 40 倍，评测时间也从 8 分钟压到 2 分钟。

**故事 3：评测本身也会错**
> 关键词判定连续三次把正确答案判错，因为模型用了"失实""超出""无"这些我没列的词。
> 后来改成 rubric + LLM 判定，并且必须把"当前日期"和"工具实际返回"喂给判定器——
> 否则它会把正确引用工具数据的回答判成编造。

## 还没做的

- 多轮用例只判最后一轮，中间轮次没有单独判定
- 没有并发压测；`/chat` 现在是串行执行（正确性优先），多会话隔离还没做
- 没有 token 成本统计（能看到调用次数，拿不到 token 数）
- RAG 只做了离线单测，没有评测集；query 改写的实际增益没量过
