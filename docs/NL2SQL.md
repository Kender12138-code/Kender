# NL2SQL：用自然语言查询本地业务库

> 一句话：**不是让模型写 SQL，而是让模型的输出可以被信任。**

## 1. 它解决什么问题

不会写 SQL 的人说一句"最近 7 天哪个商品卖得最好"，系统自动翻译成可执行、
经过安全校验的 SQL，执行后返回结果，必要时再生成一句话总结。

```
用户问题 → ① 意图/槽位 → ② 生成 SQL → ③ 六道校验 → ④ 执行 → 结果
                                            ↑ 拦不住就报错，绝不放行
```

## 2. 为什么难（实测暴露的四个坑）

| 坑 | 表现 | 解法 |
|---|---|---|
| **静默答错**（最危险） | 问"库存表"，库里没这表，它不报错，自己拼一个"销量排行"返回 | SYSTEM 强制 `SELECT 'NO_TABLE'` + few-shot 放反例 + **表名白名单** |
| 字段含义猜错 | 把"卖得最好"理解成销量还是销售额，模型自己替你决定 | schema 里给**每表 2 行真实样例**；歧义交给意图层追问用户 |
| 相对时间写死 | "上个月"被写成具体日期，过几天就失效 | 强制用 `date('now','start of month','-1 month')` 系列函数 |
| 多表 JOIN 漏条件 | 少个 ON 条件产生笛卡尔积，数字虚高几十倍还能查出来 | few-shot 给正确 JOIN 样例 + 结果行数 sanity check |

## 3. 四层设计

| 层 | 职责 | 代码位置 |
|---|---|---|
| 意图层 | 抽槽位（表/指标/时间/排序），缺条件追问用户 | 目前由 prompt 隐式完成，待显式化 |
| 转换层 | 人话 → SQL | `src/db_tool.py: nl2sql()` |
| 校验层 | 六道防线 + EXPLAIN 验语法 + 报错回喂自纠一次 | `src/db_tool.py: _validate()` |
| 评测层 | 标准问题集对比**执行结果** | `bench_nl2sql.py` |

### 六道防线

1. 只读连接 `mode=ro`（数据库层硬保证）
2. 只允许 SELECT / WITH
3. 危险关键字黑名单（`drop/delete/update/insert/...`）
4. **表名白名单**（引用了库里不存在的表 → 拦截）
5. 强制 LIMIT（无 LIMIT 就补）
6. 执行前 `EXPLAIN QUERY PLAN` 验语法

> 口诀：**只读连接打底，只放行 SELECT；黑名单挡危险，白名单防瞎编；没 LIMIT 就补上，先 EXPLAIN 再执行；报错回喂改一次，改不好就报错不硬撑。**

## 4. 怎么用

### 命令行

```bash
pip install openai python-dotenv
set DASHSCOPE_API_KEY=sk-xxxx        # PowerShell 用 $env:DASHSCOPE_API_KEY=
python nl2sql_demo.py "最近 7 天哪个商品卖得最好？"
```

### 跑基准评测

```bash
python bench_nl2sql.py --rebuild
```

判分口径：**不看 SQL 能不能跑通，看有没有答对/答错该答的题**。
我把"该拒绝却返回了别的结果"（静默答错）直接判 FAIL——这是最危险的失败模式。

### 挂到 Kender 上当成 Agent 工具

`src/db_tool.py` 暴露 `query_database(question)`，`src/agent.py` 里已经注册：

```python
try:
    from src.db_tool import query_database
    toolkit.register_tool_function(query_database)
except Exception as exc:
    print(f"[toolkit] 数据库问答工具未启用：{exc}")
```

设计要点：

- **只暴露一个工具**（传自然语言进去），不要让模型"先写 SQL 再调执行工具"——多一步多一次出错
- **异常不能往外抛**，转成文本回传，让 Agent 自己换问法或追问用户
- 结果**截断到 50 行**再进上下文，否则一张大表就撑爆窗口
- 依赖缺失时自动降级，不影响其它工具

## 5. 实测数据（qwen-plus，两表）

| 指标 | 数值 |
|---|---|
| 纯 SQL 生成 | 0.5 – 3.1 秒 |
| 全链路（含一句话总结） | 2.0 – 6.9 秒 |
| 8 题结果 | 6 题正确查询 / 2 题正确拒绝 / 0 静默错答 |

瓶颈是 LLM 调用次数而非 SQL 执行。**不需要自然语言总结时跳过第二次调用，直接省 40-50%。**

## 6. 已知边界（诚实写在这里）

- 单库单方言（SQLite），MySQL/PG 的方言差异未适配
- 意图层尚未显式化，"最好/最多"这类歧义目前靠模型默认理解，正确做法是追问用户
- 大表场景没做 schema 两级裁剪（几十张表时应先选表再给结构）
- 无缓存层，相同问题每次都要重新生成
