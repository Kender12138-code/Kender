## 版本 C：五条（详细版，投 AI 应用/Agent 岗时用）

> **Kender — 基于 ReAct 的个人 AI Agent（独立开发，已开源）**
>
> 1. **编排与工具**：AgentScope 实现 Thought/Action/Observation 循环，工具由模型自主选择而非关键词硬编码；工具 schema 由 docstring 自动生成，参数经 Pydantic 校验，缺参时主动追问。
> 2. **记忆与检索**：跨会话记忆采用「LLM 抽取 → JSON 持久化 → 回灌 system prompt」，并明确其本质是上下文注入；RAG 自建中文分块 + DashScope Embedding + FAISS，小语料自动跳过 query 改写以省 token。
> 3. **质量保障**：Critic 审核 Agent 与生成 Agent 组成评审式多 Agent；重写时把工具原始返回一并喂回，避免模型"看不到数据只能编"；复读原始数据判定为不合格。
> 4. **评测体系**：7 套件 / 71 条用例，工具调用从 agent memory 取并集（跨重试跨轮次），环境失败（超时/内容审核拦截）单独排除不计分；LLM 判定器注入当前日期与工具证据，temperature=0 保证可复现。
> 5. **性能与并发**：搜索 15s → 0.3s；FastAPI 按 session_id 隔离会话（LRU 8），同会话串行防串台、跨会话并行不互堵；单轮 120s 超时兜底。

## 面试被追问时怎么答

**Q：你说通过率 100%，是不是自己出题自己答？**
> 是自建评测集，所以我不拿它当"模型能力"的证明，而是当"回归防线"——它能挡住退化。
> 更值得说的是它**抓到过什么**：模型编造天气、Critic 重写后丢工具记录、消息 ID 秒级时间戳撞车，
> 这三个靠人工点界面很难发现。

**Q：71 条够吗？**
> 不够，但够用。它覆盖 7 类能力，每类都有"必须失败"的用例（越权、抗幻觉、闲聊不该调工具）。
> 真正的价值是**可重复**：改一版 prompt 跑一遍，两分钟出结果，而不是凭感觉。

**Q：为什么搜索从 15 秒降到 0.3 秒？**
> 先量再改。ddgs 聚合多后端，实测 12–24 秒还经常超时；换成 cn.bing.com 网页结果 0.3 秒。
> 做成 provider 链 + 兜底 + 缓存，失败自动跳过。**测量这一步比优化本身重要**——我一开始也以为是网络慢。

**Q：多会话隔离怎么做的？**
> 原来所有请求共用一个 agent + 一把全局锁，A 问长问题 B 只能等，还会共写一份 memory。
> 改成 OrderedDict 会话表，每会话独立 agent/记忆/锁，LRU 8。
> 有个细节：memory 按轮次追加，所以**同会话必须串行**，否则 A 的 tool_use 会插进 B 的对话。

**Q：最难的 bug 是哪个？**
> 消息 ID 用秒级时间戳，两轮在 1 秒内完成时 ID 重复，AgentScope 把第二条用户消息当重复消息吞掉，
> 模型看到的上下文停在自己上一句，于是原样再问一遍。
> 定位靠的是**耗时差异**：失败 1.3 秒、成功 6 秒——行为异常和耗时异常对上，才找到真正的位置。

## 注意

- 面试别说"我做的 Agent 准确率 100%"，说"**自建 71 条回归用例全部通过**"，性质完全不同。
- 也别把 eval 说成"业界 benchmark"，它是项目自建的回归防线。
- 如果被问"为什么不测 token 成本"：坦白说流式响应拿不到 usage，非流式又要牺牲体验，
  当前用「工具调用次数 + 轮次」近似衡量成本。
